# Fixtures — independent evidence, not self-confirming round trips

**Status: ACTIVE TESTING POLICY. Introduced after PR #3 mutation testing exposed a shared-assumption blind spot.**

A fixture exists to falsify an implementation assumption. If the fixture is generated through the same assumption, constant, helper, or code path as the implementation, it may only prove self-consistency.

PR #3 (`91c36b8f4168349e6893a9911a3f60075d62d973`) demonstrated the failure mode directly: an exhaustive FP4 test still missed a reversed nibble convention because both the fixture packer and the decoder were compiled from the same nibble-order macro. Flipping the convention changed both sides together, so all 16 E2M1 codes continued to pass.

The repaired test pins the layout with raw byte `0x21` and expected logical values written independently of the pack helper.

This document generalizes that lesson to every future DeepSeek fixture.

---

## 1. The core rule

For each semantic claim, the expected side must be independent of the code or convention being tested.

Bad structure:

```text
our packer ──> bytes ──> our decoder ──> compare to original values
     │                      │
     └──── same convention ─┘
```

A round trip can pass when both directions are wrong in the same way.

Preferred structure:

```text
public spec / official reference / literal bytes
                    │
                    ▼
             frozen expected result
                    │
                    ▼
              implementation under test
```

When an official oracle is unavailable, use independently derived spec values or literal encodings for the portion the spec actually settles, and label everything else unresolved.

---

## 2. Fixture classes

Every committed fixture should belong to one of these classes.

### A. Spec-derived literal fixture

Use when the public format itself fully defines the result.

Examples:

- E2M1 code `0x2` must decode to `1.0`;
- E4M3FN `0x7E` must decode to `448.0`;
- UE8M0 `0x7F` must decode to `1.0`;
- a raw byte `0x21` under a deliberately stated low-nibble-first convention maps column 0 to code 1 and column 1 to code 2.

The expected result must be written from the external definition/literal, not generated by the production decoder.

Evidence state: normally **SYNTHETIC-VERIFIED**.

### B. Checkpoint-header fixture

Use to prove tensor inventory/shape/storage facts.

Source:

- official safetensors index/header bytes from the pinned checkpoint.

Expected values should include literal tensor names, dtypes, shapes, offsets, and shard identity taken from the official artifact.

Do not derive the expected checkpoint layout from README dimensions and then claim the fixture verifies the checkpoint. That only proves the README can reproduce itself.

Evidence state: **CHECKPOINT-VERIFIED** once sourced from the real pinned artifact.

### C. Official-oracle fixture

Use for model arithmetic and DeepSeek-specific conventions.

Source:

- pinned official `inference/` or `encoding/` code;
- exact checkpoint revision where weights are required.

Examples:

- nibble order/scale direction;
- decoded real weight tile;
- one quantized projection;
- router IDs/weights;
- mHC output;
- attention intermediates;
- final logits;
- exact encoded token sequence.

Evidence state: **CHECKPOINT-VERIFIED** or **END-TO-END-VERIFIED**, depending on scope.

### D. Synthetic structural fixture

Use to exercise bounds, parser behavior, cache identity, record layout, resumability, and failure handling when the exact model values do not matter.

Examples:

- `tools/make_inventory_fixture.py`;
- synthetic `.waste` model used by upstream/model-free tests;
- corrupted record headers.

These fixtures are valuable, but they must not be promoted into checkpoint facts.

Evidence state: **SYNTHETIC-VERIFIED**.

## 3. Independence dimensions

A fixture can accidentally share assumptions in several ways.

### Shared constant

Example: packer and decoder both read the same `LOW_NIBBLE_IS_EVEN` macro.

Fix: include at least one raw encoded byte and expected logical interpretation that does not pass through the macro.

### Mirrored implementation

Example: Python fixture generator copies the same branch/table/math as the C implementation.

Fix: derive expected values from a different representation of the rule, or use official reference output.

`tests/test_quant.c` intentionally computes E2M1/E4M3 expected values algebraically while the implementation may use different local mechanics.

### Shared configuration assumption

Example: synthetic inventory generator uses README's 43×256 expert geometry, and the inventory tool reproduces 43×256.

That proves the inventory arithmetic and classification machinery on a fixture of that shape. It does **not** prove the actual checkpoint has that shape.

Fix: real Gate V0 must consume official names/headers.

### Shared parser

Example: serializer and parser under test both use the same schema helper.

Fix: freeze malformed and valid literal byte sequences independently, including boundary cases.

### Shared tokenizer/template

Example: a DeepSeek encoder port generates its own expected token IDs using the same helper it is testing.

Fix: official `encoding/` output becomes the fixture; the port consumes it but never generates its own expected answer.

## 4. Minimum provenance for committed oracle fixtures

Every official-derived fixture must carry enough metadata to regenerate it.

Recommended sidecar fields:

```json
{
  "fixture_version": 1,
  "model_repo": "deepseek-ai/DeepSeek-V4-Flash-0731",
  "model_revision": "<resolved commit sha>",
  "source_path": "inference/kernel.py",
  "source_sha256": "<hash>",
  "config_sha256": "<hash>",
  "operation": "fp4_decode",
  "device": "cpu|cuda:<id>",
  "dtype_policy": "<exact reference settings>",
  "seed": 0,
  "input_description": "<human-readable>",
  "generator_commit": "<this repo commit>",
  "generated_at": "<UTC timestamp>"
}
```

For fixtures whose input bytes are the evidence, commit the input bytes or a stable hash plus an unambiguous retrieval recipe.

Do not depend on a moving `main`/`latest` branch in a golden fixture.

---

## 5. Freeze inputs and expected outputs separately

A useful layout is:

```text
tests/fixtures/deepseek_v4/
  fp4_nibble_order/
    input.bin
    expected.json
    provenance.json
  fp8_scale_direction/
    weight.bin
    scale.bin
    x.f32
    expected_y.f32
    provenance.json
  router_case_001/
    input.f32
    expected_ids.i32
    expected_weights.f32
    provenance.json
```

The test executable should read the frozen artifacts and compare. It should not invoke the generator during the test and then compare the implementation to output generated seconds earlier by a potentially shared bug.

Generator scripts are useful for regeneration, but generated results should be reviewable diffs/artifacts.

---

## 6. Convention fixtures must be literal

Any convention with two or more plausible interpretations needs a literal fixture.

Examples for this port:

- low nibble vs high nibble first;
- multiply scale vs divide scale;
- row-major vs transposed scale grid;
- scale before vs after another transform;
- expert `w1/w2/w3` orientation;
- token-id hash table indexing/base;
- top-k tie ordering;
- compressed-attention index ordering;
- special-token markup/content boundary.

A convention fixture should be small enough that a reviewer can inspect it manually.

For example, PR #3's nibble fixture is intentionally only one byte:

```text
0x21 -> [0.5, 1.0] under the currently documented layout
```

That is more valuable for convention detection than megabytes of self-generated random packed values.

## 7. Mutation testing policy

Mutation testing is not required for every line, but it is strongly recommended at semantics that fail silently.

Prioritize mutations for:

- bit shifts/masks;
- nibble/byte order;
- scale multiplication/division;
- off-by-one block indexes;
- transpose/stride selection;
- router top-k ordering;
- cache key identity;
- container offsets/lengths;
- tokenizer special-token mode;
- parser state transitions.

For each high-risk seam, ask:

```text
What single-line wrong implementation would still produce plausible values?
Does at least one test kill it?
```

A mutation that survives should be treated as evidence that the fixture is insufficient, not merely as a test-coverage percentage issue.

### PR #3 record

Ten one-line decoder mutations were tested. Nine were caught initially. The surviving nibble-order mutation revealed a shared-assumption fixture. After adding the literal raw-byte assertion, all ten were caught.

This result is logged in `docs/EXPERIMENTS.md` entry 3 and should remain a template for future silent-convention work.

---

## 8. Fixture generator review checklist

Before trusting a new generator, reviewers should answer:

- What external source settles the expected result?
- Does the generator import any header/module from the implementation under test?
- Does it read a constant that the runtime also reads?
- Is a round trip being mistaken for correctness?
- Are literal boundary cases present in addition to random cases?
- Could both generator and runtime be transposed/reversed/scaled incorrectly together?
- Is the fixture labeled synthetic vs checkpoint/oracle derived?
- Is the source revision pinned?
- Can a later contributor regenerate it without guessing environment settings?
- Would a known wrong implementation fail?

If the answer to the last question is unknown, mutation-test the seam before relying on the fixture as a gate.

---

## 9. Specific warning for `make_inventory_fixture.py`

`tools/make_inventory_fixture.py` is deliberately synthetic. It currently embodies the documented target geometry and therefore cannot validate that DeepSeek shipped that geometry.

It is still valuable for:

- parser/header-only behavior;
- classification mechanics;
- unresolved-byte handling;
- Gate V0 failure injection;
- proving no tensor data is read.

It is not evidence for:

- exact real tensor names;
- exact layer/expert counts;
- exact real shapes;
- exact byte totals;
- real DSpark namespace;
- real hash-routing tensor representation.

When real metadata becomes available, add separate checkpoint-derived fixtures rather than mutating the synthetic generator and then using the changed generator as proof of the same facts.

---

## 10. Oracle generation boundary

When official DeepSeek access is restored, generator code should be kept outside the C implementation path.

Preferred flow:

```text
official DeepSeek Python reference
          +
pinned checkpoint/reference inputs
          ↓
fixture generator wrapper
          ↓
frozen binary/json artifacts
          ↓
C tests
```

The C tests should not require torch, CUDA, Hugging Face access, or the full checkpoint to replay already-generated small fixtures.

That makes the expensive/online oracle generation occasional, while the correctness check stays cheap and deterministic in normal development.

---

## 11. When the official reference disagrees with a local literal

A local literal may intentionally encode an unresolved current convention. When official source proves a different convention:

1. cite the exact official path/revision/line or generated oracle artifact;
2. add/update the official fixture first;
3. demonstrate that the old implementation fails the official fixture;
4. update the implementation;
5. update the local literal so it now states the verified convention;
6. record the result in `docs/EXPERIMENTS.md` if it corrects a significant prior assumption;
7. update `docs/NUMERICS.md`, `docs/TENSOR_MAP.md`, and `docs/VALIDATION.md` evidence state.

A failing old assertion in this situation is a successful gate: it prevented a silent convention change.

---

## 12. Merge standard

For a new arithmetic/model fixture to become part of a gate, it should have:

- a clear fixture class;
- independent expected values;
- pinned provenance;
- literal boundary/convention cases where applicable;
- deterministic replay without external network access where practical;
- a documented wrong implementation or mutation that it would catch;
- evidence state recorded in the relevant docs.

The goal is not the largest fixture corpus. The goal is the smallest set of independent fixtures that makes plausible wrong implementations fail early.
